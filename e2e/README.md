# Интеграционные тесты (Playwright)

Интеграционные (e2e) тесты проверяют, что фронтенд и бэкенд работают вместе:
тесты запускают реальный Go-бэкенд и Vite-фронтенд и проходят пользовательские
сценарии через интерфейс браузера. API-вызовы в тестах идут через фронтенд-прокси
`/api`, то есть проверяется весь путь браузер → Vite → Go-бэкенд.

## Запуск

```sh
npm install
npm run test:e2e:install     # однократно: установка браузера Chromium
npm run test:e2e             # безголовый прогон
npm run test:e2e:headed      # с видимым окном браузера
```

Что происходит при прогоне:

- Playwright сам поднимает бэкенд (`go run ./cmd/server` на `127.0.0.1:4010`)
  со **свежей БД** в `/tmp/callcalendar-e2e-<pid>.db` и Vite-сервер
  (`npm run dev` на `:5173`). Порты 4010/5173 должны быть свободны —
  `reuseExistingServer: false`.
- `workers: 1` — тесты выполняются последовательно: между тестами данные
  очищаются через API (удаление всех типов событий, каскадно удаляющее брони).
- Время слотов тесты получают из живого API/UI (бэкенд фильтрует прошлые слоты
  по UTC), поэтому даты в тестах не хардкодятся.

Тесты пишутся на TypeScript и не попадают в `tsconfig` (build их не проверяет).
`npm run build` и `go test ./...` остаются прежними проверками.

## Сценарии

### Гость

| Код | Сценарий |
|-----|----------|
| G1  | Гость видит список видов брони (название, описание, длительность, окно записи) и переходит к слотам выбранного типа. |
| G2  | Полный путь бронирования: выбор свободного слота → ввод имени и email → «Запись подтверждена» → слот исчезает из сетки и из ответа `/slots`. |
| G3  | Конфликт (409): две вкладки открыты на один слот; первая бронирует успешно, вторая получает ошибку «Выбранное время уже занято». |

### Администратор

| Код | Сценарий |
|-----|----------|
| A1  | `/admin` без входа редиректит на `/admin/login`; неверный пароль → ошибка; `admin`/`admin` → страница предстоящих встреч; выход возвращает на форму входа. |
| A2  | Бронь, созданная гостем, видна в таблице предстоящих встреч (гость, email, тип события). |
| A3  | Админ отменяет бронь через модалку подтверждения — запись исчезает. |
| A4  | Создание типа события через форму → появляется в админ-таблице и на гостевой странице. |
| A5  | Редактирование типа события → новое имя отображается в таблице, старое исчезает. |
| A6  | Удаление типа события → исчезает из списка, его бронирования удалены каскадно (`GET /admin/bookings` пуст). |

### Контракт API (через фронтенд-прокси)

| Код | Сценарий |
|-----|----------|
| E1  | Слоты несуществующего типа события → 404. |
| E2  | Бронь вне сетки слотов → 422. |
| E3  | Повторная бронь того же слота → 409. |
| E4  | Неверный логин администратора → 401. |

## CI

`.github/workflows/tests.yml` запускается на каждый push (все ветки) и на каждый
pull request и состоит из двух джоб:

- `backend` — `go vet ./...` и `go test ./...` (Go 1.22 из `backend/go.mod`).
- `e2e` — `npm ci`, установка браузеров, `npm run test:e2e`. Перед тестами
  выполняется `go build ./...`, чтобы разогреть кэш сборки Go для `go run`
  внутри `webServer`. При провале на артефакт выгружается `playwright-report/`
  и `test-results/` (ретенция 7 дней).

`hexlet-check.yml` (генерируемый файл Hexlet) не редактируется.
